# rem0000 multi-tenancy

**branch:** rem0000-multi-tenancy · **status:** planning (design first, build last)
**order:** design → rem0001 → rem0003 → rem0002 → rem0004 → implementation

## goal

each tenant (business) has its own content, users, access, and branding across the admin panel and the frontend.

## notes from owner

- user access records (`users-access`) should be assigned to users. see rem0001.

## approach (draft)

- evaluate `@payloadcms/plugin-multi-tenant` first. it's official, adds a tenant field + tenant selector to collections, and adds `users.tenants[]`.
- the old project's `operator` → `restaurant` hierarchy is effectively tenant → location. decide whether locations are their own collection.
- decide what is tenant-scoped and what is shared:
  - tenant-scoped: pages, posts, media, categories, header, footer, theme, settings, menu, pos data, audit logs
  - shared or super-user only: tenants, users?, users-access?
- globals (header, footer, theme, settings) can't be per-tenant as payload globals. they likely become tenant-scoped collections with one doc per tenant. the plugin supports this via `isGlobal`.
- frontend: resolve the tenant from the domain or subdomain in middleware.

## open questions

- [ ] can one user belong to multiple tenants with different access in each? this decides the user ↔ access shape in rem0001.
- [ ] tenant resolution: custom domain, subdomain, or path prefix?
- [ ] are super users platform-level only, or can a tenant have its own super user?
- [ ] data migration: which tenant does the existing content belong to?
